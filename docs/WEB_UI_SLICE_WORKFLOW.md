# Как выполнять и проверять Web UI-срезы Selara

> [!IMPORTANT]
> Этот документ обязателен для ИИ, агентов и разработчиков, которые меняют
> серверный Web UI Selara. Перед началом среза необходимо полностью прочитать
> `docs/WEB_UI_MODERNIZATION_TODO.md` и этот файл.
>
> Срез нельзя считать завершённым только потому, что код написан и тесты зелёные.
> Его необходимо отрендерить, вручную посмотреть на изображения, исправить
> найденные визуальные проблемы, повторить рендер и сохранить финальные результаты.

## 1. Что считается срезом

Срез — это законченная пользовательская возможность или состояние страницы,
которое можно проверить вертикально:

1. серверный контракт и данные;
2. Jinja-разметка;
3. CSS и JavaScript;
4. функциональность и защита от ошибочных действий;
5. responsive-поведение;
6. accessibility;
7. визуальный результат;
8. тесты, линтеры и запись в общем TODO.

Размер среза выбирается так, чтобы его результат можно было увидеть и проверить
отдельно. Несвязанные страницы и бизнес-логику в один срез не объединять.

## 2. Подготовка

Перед изменениями исполнитель обязан:

1. Полностью прочитать `docs/WEB_UI_MODERNIZATION_TODO.md` и этот документ.
2. Проверить `git status` и сохранить все уже существующие изменения пользователя.
3. Выбрать следующий пункт согласно зафиксированным приоритетам roadmap.
4. Записать точный объём среза, его состояния и критерии готовности.
5. Пометить задачу `[~]` в TODO и добавить строку в начало журнала работ.
6. Определить, какие существующие URL и backend-контракты должны сохраниться.
7. Зафиксировать обязательные состояния: normal, empty, error, long content,
   permission/session failure, loading/submit и mobile/tablet — где применимо.

Существующий грязный worktree не очищается и не перезаписывается. Изменения других
задач считаются принадлежащими пользователю, пока не доказано обратное.

## 3. Tests-first

Сначала добавляются тесты, описывающие новый контракт и пользовательское поведение.
Первый запуск должен падать по ожидаемой причине: отсутствует нужная разметка,
endpoint, стиль или действие. Этот запуск подтверждает, что тест действительно
защищает новую возможность.

Минимальный набор по применимости:

- route/unit-тест серверного контракта, авторизации и ошибок;
- render/security-тест Jinja и безопасного escaping;
- Playwright-тест основного действия и keyboard flow;
- проверка double submit, повторного клика или восстановления после ошибки;
- desktop, mobile и tablet geometry/no-overflow;
- empty, long string, недоступные optional-данные;
- ограничитель размера нового CSS/JavaScript-файла, если создаётся page asset.

После реализации сначала запускаются узкие тесты среза, затем связанные тесты
страницы, и только после этого — весь `tests/unit`.

## 4. Реализация

Реализация выполняется от контракта к представлению:

1. Подготовить минимальные данные страницы без лишних запросов и ложных статусов.
2. Добавить семантическую Jinja-разметку и доступные названия controls.
3. Вынести page-specific CSS и JavaScript в статические файлы.
4. Сохранить keyboard flow, видимый focus и touch targets не меньше 44 CSS px.
5. Обработать session expiry, server/Telegram error и повторные действия.
6. Не раскрывать в DOM секреты, Telegram `file_id`, session tokens и приватные raw
   данные без явной административной необходимости.
7. Не использовать цвет как единственный носитель статуса.
8. Не добавлять автоматическую загрузку тяжёлых или приватных media без необходимости.

Если во время среза найден общий дефект, его разрешено исправить только когда он
необходим для корректного результата текущего среза. Причина записывается в журнал.

## 5. Как создаются изображения результата

Для визуального цикла используется воспроизводимый Playwright fixture с безопасными
тестовыми данными. Он должен показывать реальные состояния компонента, но не должен
обращаться к production-БД, Telegram или внешней сети.

Обязательные размеры по применимости:

- desktop Chromium — `1440×900`;
- современный Android/mobile Chromium — обычно `390×844`;
- tablet — обычно `820×1180`;
- Mobile WebKit/iPhone и Tablet WebKit/iPad — когда WebKit установлен и включён в
  текущую тестовую матрицу.

Дополнительно снимаются не только начальные страницы, но и важные состояния:

- открытый dialog/drawer/details;
- заполненная форма или загруженный preview;
- validation/backend error;
- empty state;
- длинный контент и крайняя ширина;
- loading/disabled state, если он визуально значим.

Перед screenshot нужно дождаться шрифтов, layout и переходов. Для стабильных кадров
Playwright screenshot выполняется с отключёнными анимациями. Динамические ID, время,
таймеры и приватные значения заменяются детерминированными fixture-данными.

## 6. Где изображения создаются и как называются

Первичный рендер сохраняется во временную папку:

```text
/tmp/<имя_среза>_screens/
```

Пример:

```text
/tmp/admin_overview_screens/
```

Имя каждого файла начинается со следующего свободного сквозного номера общей серии:

```text
39_admin_feedback_desktop.png
40_admin_feedback_mobile.png
41_admin_feedback_error.png
```

После финальной ручной проверки файлы копируются в постоянную папку пользователя:

```text
/home/beykus/selara_screen/
```

То есть сокращённо — `~/selara_screen`. Копирование выполняется без удаления уже
существующих результатов. Старые номера и файлы не перезаписываются другим срезом.

Временный render-скрипт обычно находится в `/tmp/render_<имя_среза>_screens.py`.
Если fixture нужен тестам или CI постоянно, его переносят в `scripts/` и добавляют
соответствующие проверки. Временный скрипт сам по себе не является результатом
среза; результатом являются код, тесты, обновлённый TODO и финальные изображения.

Изображения в `~/selara_screen` — локальные review-артефакты. Они не добавляются в
Git автоматически. Добавление бинарных snapshots в репозиторий требует отдельного
решения о стабильной visual-regression среде.

## 7. Как изображения проверяются и сравниваются

Каждый созданный PNG нужно открыть инструментом просмотра изображений. Недостаточно
проверить только наличие файла, размеры или успешный exit code Playwright.

Просмотр выполняется по одному состоянию или небольшой логической группе. Для
каждого изображения проверяются:

- визуальная иерархия и читаемость без повторного перечитывания;
- отсутствие дублирующей информации и одинаковых preview;
- обрезка текста, кнопок, рамок, скруглений и focus outline;
- отсутствие горизонтального page overflow;
- нормальный перенос длинных имён, ID, URL, emoji, CJK и RTL;
- единые цвета, поверхности, отступы, радиусы и состояния controls;
- отсутствие нативных browser-стилей, случайно перебивших компонент;
- доступность основных действий без hover;
- положение dialog и действий в пределах mobile viewport;
- отсутствие промежуточных кадров transition, paint-артефактов и битых media;
- соответствие empty/error/loading состояния реальному смыслу.

Desktop, mobile и tablet сравниваются между собой не попиксельно, а по сохранению
иерархии и функций. Desktop не должен быть просто растянутой мобильной колонкой, а
mobile не должен терять действия или требовать горизонтальной прокрутки.

Также результат сравнивается с предыдущими PNG того же экрана в
`~/selara_screen`: не вернулась ли уже исправленная проблема, не исчезло ли действие,
не ухудшилась ли плотность или читаемость. Если автоматические visual snapshots пока
не настроены, это ручное сравнение является обязательным.

## 8. Итерационный визуальный цикл

После первого просмотра исполнитель составляет конкретный список дефектов и повторяет
цикл:

1. Исправить один или связанную группу дефектов.
2. Добавить regression-тест, если дефект можно проверить через DOM/geometry/state.
3. Перезапустить узкие тесты и линтеры.
4. Повторно отрендерить все затронутые viewport/state, а не только один кадр.
5. Снова открыть и посмотреть обновлённые изображения.
6. Повторять до отсутствия известных блокирующих визуальных дефектов.

Если screenshot содержит браузерный paint/transition-артефакт, сначала нужно доказать,
что DOM и geometry корректны, затем повторить стабильный рендер с отключёнными
анимациями. Если повреждение воспроизводится периодически именно в длинном пакетном
рендере, каждый проблемный state снимается в отдельном browser context или процессе;
при необходимости Chromium запускается без GPU. После этого новый PNG снова
просматривается вручную. Нельзя молча принять повреждённый кадр как финальный.

## 9. Финальные проверки среза

Перед `[x]` выполняются:

- целевые route/unit/browser/security-тесты;
- весь связанный набор страницы;
- ESLint для server JavaScript;
- Stylelint для всех подключённых server CSS, включая новый файл;
- HTMLHint на representative rendered HTML;
- frontend build, если менялся frontend toolchain или общие assets;
- Python compile/check, если менялся серверный код;
- полный `tests/unit`;
- `git diff --check`;
- финальный повторный просмотр сохранённых PNG.

Количество тестов, viewport-сценариев и изображений записывается в журнал работ.
Если какая-то обязательная матрица пока технически недоступна, это указывается честно,
а пункт остаётся `[~]` или отдельной незакрытой задачей.

## 10. Завершение и передача результата

После проверок исполнитель:

1. Меняет только фактически выполненные пункты `[~]` на `[x]`.
2. Обновляет процент этапа и общий процент по фактическим дочерним задачам.
3. Записывает в журнал: тесты, линтеры, build, число PNG и важные решения.
4. Проверяет, что финальные PNG находятся в `~/selara_screen`.
5. В ответе даёт кликабельные ссылки на основные изображения.
6. Явно сообщает, выполнялись ли commit, push и deploy.

Коммит, push и deploy не выполняются автоматически только из факта завершения среза:
для них нужна текущая команда пользователя.
