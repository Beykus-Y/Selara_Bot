## 1. Цель

Обновить весь серверный Web UI Selara, сделать его современнее, удобнее и
последовательнее, сохранив узнаваемый тёмный неоновый стиль проекта.

Главные результаты:

- функциональная и визуально цельная серверная админка;
- история сообщений, читаемая как лента группового диалога, а не таблица БД;
- единая пользовательская и администраторская документация с поиском;
- полноценная адаптация для современных смартфонов и планшетов;
- проверяемая доступность, семантика, адаптивность и производительность;
- единая система компонентов вместо несвязанных шаблонов, inline-стилей и
  монолитного CSS;
- отсутствие дублирующихся активных реализаций одного интерфейса.

## 2. Зафиксированные решения

Эти решения подтверждены пользователем 2026-08-15.

### Архитектура

- [x] Серверные страницы `/app`, админка и документация остаются на Jinja.
- [x] React остаётся интерфейсом Telegram Mini App (`/miniapp`).
- [x] Неиспользуемые React-копии серверной админки и документации подлежат удалению
  только после инвентаризации зависимостей и подтверждения функционального паритета.
- [x] Новый переключатель между старым и новым дизайном не нужен.
- [x] Существующие URL, авторизация и серверные сценарии должны сохраняться при
  последовательной замене страниц.

### Приоритеты

1. Серверная админка.
2. Внутри админки: системные рассылки и история сообщений.
3. Пользовательская и администраторская документация.
4. Остальные серверные страницы.
5. Игровые страницы — после стабилизации общей системы компонентов.

### Визуальное направление

- [x] Сохранить тёмную неоновую идентичность Selara.
- [x] Освежить визуальный язык: меньше декоративного шума, яснее иерархия,
  современная типографика, более спокойные поверхности и выразительные состояния.
- [x] Проектировать mobile-first, но не превращать desktop-интерфейс в растянутую
  мобильную колонку.
- [x] Поддерживать современные смартфоны и планшеты.
- [x] Обязательные браузерные семейства: Chrome/Chromium и Safari/WebKit.

### История сообщений

- [x] Основное представление — список чатов и читаемая лента сообщений.
- [x] Нужны группировка по датам, авторы, время, reply-контекст, редакции, поиск и
  фильтры.
- [x] Нужны превью поддерживаемых медиа и понятный fallback, если файл недоступен.
- [x] Raw JSON остаётся доступным как отдельный технический режим, но не является
  основным представлением.
- [x] Сохранение всех исходящих сообщений бота отложено на будущий этап.
- [x] На текущем этапе интерфейс использует уже сохраняемые входящие сообщения и
  снимки редакций. Он не должен вводить администратора в заблуждение и называться
  полной копией истории Telegram.

### Документация

- [x] Нужны отдельные пользовательская и администраторская области.
- [x] Пользовательская документация должна быть доступна без административного
  входа, если материал не раскрывает защищённые данные.
- [x] Нужен полнотекстовый поиск.
- [x] Нужны оглавление, стабильные anchors/deep links и мобильная навигация.
- [x] Команды, настройки и описания должны получать данные из единого источника,
  чтобы Jinja, Mini App и бот не расходились вручную.

### Качество

- [x] Stylelint для CSS.
- [x] djLint с Jinja-профилем для исходных шаблонов.
- [x] HTMLHint для отрендерированного HTML, где он даёт полезный сигнал без ложных
  срабатываний на Jinja.
- [x] ESLint для вынесенного серверного JavaScript.
- [x] Playwright для функциональных, responsive и визуальных сценариев.
- [x] axe-core для автоматически проверяемой части WCAG A/AA.
- [x] Lighthouse CI: сначала отчёты и baseline, затем согласованные бюджеты.
- [x] Автоматические проверки не заменяют ручную проверку клавиатуры, читаемости,
  порядка фокуса и сложных responsive-состояний.

### Выкладка

- [?] Стратегия первой production-выкладки нового интерфейса пока не определена.
- [x] Feature flag или пользовательский переключатель старого/нового дизайна не

- [ ] До начала production-выкладки отдельно согласовать размер первого релиза,
  порядок миграции страниц и способ отката.

## 3. Текущая техническая база

Инвентаризация на 2026-08-15:

- 21 Jinja HTML-файл в `src/selara/web/templates`;
- около 6 206 строк Jinja/HTML;
- `src/selara/web/static/panel.css` — около 6 145 строк;
- около 1 942 строк inline-JavaScript в пяти шаблонах;
- 38 inline-атрибутов `style`;
- таблицы используются в `chat.html`, `admin_table.html` и
  `admin_messages_compact.html`;
- текущий Python Playwright используется точечно, полноценной матрицы серверного UI
  пока нет;
- React-исходники содержат старые/параллельные страницы админки и документации, но
  активный router Mini App их не публикует;
- Jinja autoescape включён, но тестовый режим с `StrictUndefined` не настроен;
- адаптивные правила существуют, но покрывают лишь отдельные области большого
  монолитного stylesheet.

Самые рискованные по объёму шаблоны:

- `_games_dashboard.html` — около 1 244 строк;
- `chat.html` — около 1 321 строки и большой inline-JavaScript;
- `games.html` — около 964 строк JavaScript поверх крупного partial;
- `admin.html` — около 385 строк после extraction и добавления preview/confirm;
- `economy.html` — около 353 строк.

## 4. Общие правила реализации

- [ ] Не выполнять массовый rewrite всех страниц одним коммитом.
- [ ] Следовать полному workflow из `docs/WEB_UI_SLICE_WORKFLOW.md`, включая ручной
  просмотр каждого финального screenshot и сохранение в `~/selara_screen`.
- [ ] Работать вертикальными срезами: тесты и состояние до изменения → компоненты →
  страница → responsive → accessibility → проверки → обновление TODO.
- [ ] Сохранять существующие серверные маршруты и backend-контракты, если изменение
  контракта не согласовано отдельно.
- [ ] Не смешивать редизайн с несвязанными изменениями бизнес-логики.
- [ ] Не скрывать технические возможности generic DB explorer; отделить их от
  продуктовых представлений.
- [ ] Не использовать цвет как единственный способ передачи статуса.
- [ ] Все интерактивные элементы должны работать с клавиатуры и иметь видимый focus.
- [ ] Touch targets основных действий — не менее 44×44 CSS px либо эквивалентная
  удобная зона нажатия.
- [ ] Горизонтальная прокрутка всей страницы запрещена. Она допустима только внутри
  явно обозначенного технического контейнера таблицы.
- [ ] Длинные Telegram-имена, непрерывные строки, emoji, RTL/CJK, пустые данные и
  большие наборы записей входят в обязательные тестовые состояния.
- [ ] Все destructive-действия имеют понятное подтверждение, описание объекта и
  безопасное восстановление фокуса после закрытия диалога.
- [ ] Визуальные эффекты учитывают `prefers-reduced-motion`.
- [ ] Секреты, сессионные данные и приватное содержимое не попадают в публичные
  Lighthouse/Playwright-артефакты.
