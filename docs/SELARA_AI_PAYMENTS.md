# Selara AI через Telegram Stars

## Продукт

- Один продукт: `selara_ai_monthly`.
- Entitlement принадлежит чату и действует 30 дней; покупатель хранится отдельно
  в записи платежа.
- Повторная покупка прибавляет 30 дней к ещё активному сроку. Если срок уже
  закончился, новый период начинается со времени Telegram payment message.
- Автопродления нет. По истечении срока resolver возвращает бесплатный tier.
- Paid tier включает scheduled Daily Summary и остаётся виден общему access layer
  для `?` / `??`. Пока отдельная paid quota не задана, действуют текущие лимиты:
  10 запросов LLM в день и 10 ручных `/summary` за календарный месяц. Resolver
  может передать отдельную paid quota policy; её лимит оставлен незаданным до
  продуктового решения.
- Перед выставлением счёта пользователь открывает `/terms` (условия также доступны
  кнопкой из экрана покупки) и явно подтверждает их. Purchase intent хранит
  принятую версию условий и время согласия. Текущая версия условий — `v2`;
  она также сообщает о зависимости AI-функций от настроенного и доступного провайдера.
- Команды `/terms` и `/paysupport` доступны пользователю; `/paysupport` направляет
  запрос через существующую очередь `/feedback поддержка: ...`.
- Owner exemption проверяется отдельно и не создаёт фиктивные entitlement или
  payment rows. Обычная STT-транскрипция остаётся бесплатной и вне access gate.

## Конфигурация цены

До решения владельца цена не задаётся в коде или `.env.example`.
`SELARA_AI_PRICE_STARS` должен быть установлен в положительное целое число перед
тем, как станет доступна команда покупки. Без цены checkout закрыт. Одна цена
используется при создании purchase intent; invoice и pre-checkout сверяются с
зафиксированной в intent суммой, поэтому изменение env не портит уже выданный
счёт.

Также необходимы включённый `LLM_ENABLED` и настроенный `LLM_API_KEY`; иначе бот
не предлагает продукт, который сейчас не может обслуживать.

## Поток и восстановление

1. `/premium` доступна в личке. Бот предлагает только известные чаты, где у
   пользователя есть активность и бот числится участником.
2. До создания счёта Telegram API подтверждает, что покупатель — creator/admin,
   а бот состоит в чате и может отправлять сообщения. Эти проверки повторяются
   при `pre_checkout_query`; ошибка Telegram API закрывает покупку.
3. Purchase intent хранит buyer, исходный и текущий chat id, product, сумму,
   валюту `XTR`, duration и expiry. Versioned payload содержит только UUID этого
   intent: `selara_ai:v1:<uuid>`. Новый счёт для той же пары buyer/chat создаётся
   не чаще одного раза в минуту. Истёкшие intent сохраняются: принятый Telegram
   pre-checkout может завершиться позже срока intent, и поздний `successful_payment`
   всё равно должен быть восстановлен.
4. `pre_checkout_query` проверяет intent, buyer, валюту, сумму, expiry, сохранённое
   согласие с условиями и live authority. Проверки ограничены 6 секундами, ответ
   Telegram — 2 секундами (всего меньше 10 секунд). Если ответ потерялся в сети,
   новый query id может повторно пройти тот же неиспользованный intent; только
   `successful_payment` завершает покупку и изменяет срок entitlement.
5. Только `successful_payment` создаёт payment audit и entitlement. В одной
   PostgreSQL-транзакции записываются платёж, срок доступа и consumed state.
   Повтор с тем же `telegram_payment_charge_id` не продлевает срок второй раз.
6. Разные реальные платежи одного чата сериализуются PostgreSQL advisory lock и
   row lock. Подтверждение в Telegram отправляется после commit; её ошибка не
   откатывает доступ, а повтор update может безопасно доставить сообщение ещё раз.
7. Если DB недоступна во время `successful_payment`, обработчик удерживает этот
   update и повторяет транзакцию с экспоненциальной задержкой до 60 секунд. После
   третьей неудачи владелец получает DM; polling остаётся приостановлен до commit
   или штатной остановки процесса. Подтверждающее сообщение ограничено таймаутом.
8. Потеря admin-статуса после принятого pre-checkout не отменяет оплату:
   подтверждённый Telegram payment всё равно создаёт entitlement для чата. Если
   Telegram прислал платёж с неизвестным intent или несовпадающими buyer/суммой/
   валютой, событие сохраняется со статусом `rejected`, а покупателю показывается
   сообщение для ручной сверки с владельцем.

Group → supergroup migration переносит current chat id у purchase intents. Для
collision двух entitlements система складывает оставшееся активное время обоих
чата, сохраняя полную оплаченную длительность. Исторические payment rows остаются
неизменными и хранят source/target chat ids на момент обработки. Запрос истории
по canonical chat включает такие старые платежи через текущий chat id их purchase
intent.

## Refunds и observability

Автоматического возврата нет; история платежей доступна владельцу в Mini App Admin
(см. ниже). Миграция `0077_selara_ai_payment_refunds`
добавляет audit записи попыток возврата. Для сохранённого отклонённого платежа
владелец получает DM с номером payment record и может выполнить
`/stars_refund <payment_id>` в личке бота. Команда доступна только `ADMIN_USER_ID`,
проверяет, что платеж отклонён, и записывает единственную попытку до вызова
Telegram `refundStarPayment`. Подтверждённый результат сохраняется. Если сетевой
ответ потерян, попытка остаётся `pending`, чтобы случайный повтор не вызвал
двойной возврат; состояние нужно сверить с Stars-транзакциями. Команда не отзывает
уже применённые entitlements. Payment/entitlement repository по-прежнему позволяет
получать историю платежей, сумму Stars, число успешных оплат и число активных чатов.

## Статус Selara AI в Mini App (для группы)

На странице группы в Mini App есть отдельный блок **Selara AI**. Он грузится
независимо от остального обзора (`GET /api/miniapp/chat/{chat_id}/ai-access`) и
доступен тем, кто и так видит страницу группы. Данные берутся только из
`FeatureAccessService` и entitlement resolver; frontend ничего не пересчитывает.

- Тарифы: «Бесплатный доступ», «Активна до ДД.ММ.ГГГГ» (авторитетный
  `valid_until`; за 7 дней и меньше — «Скоро закончится»), «Внутренний доступ»
  (owner exemption: без коммерческого лимита, entitlement и платежи не создаются).
  Истёкший entitlement сразу показывается как бесплатный, с датой окончания и
  кнопкой «Продлить».
- Квоты: `? / ??` (`llm_admin`, день) и ручные `/summary` (`daily_summary`,
  `trigger=manual`, календарный месяц) — использовано / лимит / осталось / время
  сброса в `BOT_TIMEZONE`. Пока нет отдельной paid-квоты, показываются реальные
  бесплатные лимиты, а не обещания «больше запросов».
- Автоматические итоги — три независимых вещи: доступ (Selara AI), переключатель
  `daily_summary_enabled` и итоговое состояние: «Активны», «Доступны, но выключены в
  настройках», «Включены в настройках, но требуют Selara AI», «Недоступны».
- Если resolver или хранилище квот недоступны, показывается «Статус временно не
  удалось проверить», а не фиктивный free/`0/10`.
- Кнопка «Получить Selara AI»/«Продлить» видна тем, у кого есть право управления
  настройками группы, и только если задан `SELARA_AI_PRICE_STARS`. Checkout
  остаётся в личке бота: кнопка открывает чат с ботом, оплата — через `/premium`.
  Права покупателя по-прежнему проверяются вживую при создании счёта.
- Пользовательский UI не показывает токены и стоимость.

## Аналитика AI и Stars для владельца

Раздел **AI и монетизация** (`/admin/ai` в Mini App Admin, вкладка «AI», плюс
компактный блок на главной) доступен только `ADMIN_USER_ID`. Каждая секция
загружается отдельным запросом, поэтому сбой AI-учёта не скрывает платежи и
наоборот. Периоды: 24 ч, 7, 30, 90 дней (скользящее окно `[from, to)`); сброс
квот — календарный и считается отдельно.

Endpoints (`/api/miniapp/admin/…`): `ai/summary`, `ai/breakdown`, `ai/readiness`,
`monetization/summary`, `monetization/payments` (cursor, фильтры state/refund/
chat_id/buyer_id/period_days), `monetization/payments/{id}`,
`monetization/entitlements`. Все только для владельца, без raw prompt/completion,
сообщений, токенов и секретов.

- **Известная стоимость** — сумма `estimated_cost_usd` только по вызовам с ценой.
  Если есть вызовы с неизвестной стоимостью, UI не называет её «общими расходами» и
  показывает предупреждение: фактический расход выше или равен указанному. «Средняя
  известная часть стоимости» — это среднее известной части на запрос, а не
  фактическая средняя стоимость. Marker-only попытки провайдера (старт без записи
  использования) считаются вызовом с неизвестной стоимостью.
- **Неуспешные запросы** — `failed` + `partial`.
- Разбивки по функциям (список не захардкожен: новые feature появляются сами), по
  моделям (вызовы, prompt/completion tokens, стоимость, вызовы без цены) и топ
  этапов.
- **Stars**: выручка только по `applied`; отклонённые (даже с выполненным возвратом)
  не считаются выручкой. Активные платные чаты — `status=active` и
  `valid_until > now`; отдельно «истекают в ближайшие 7 дней». Rejected и состояния
  возврата (`pending`/`refunded`/`failed`) видны в истории платежей.
- Выручка в Stars (XTR) и расходы AI в USD — разные валюты. Курса нет, прибыль
  `Stars − USD` не считается, графики разнесены.
- История платежей: пагинация по `(payment_at, id)`, фильтр по чату находит и
  старый group id, и текущий supergroup id (каноничный чат берётся из purchase
  intent). Telegram charge ID виден только в деталях платежа. Для `rejected`
  платежа с возвратом `pending` показывается «Исход возврата требует ручной
  проверки»; кнопки возврата в UI нет — используйте `/stars_refund <payment_id>`.
- «Готовность Selara AI»: провайдер LLM, цена Stars, схема платежей, resolver
  доступа, учёт стоимости. Это диагностика без тестовых покупок. Без
  `SELARA_AI_PRICE_STARS` показывается «Checkout выключен: SELARA_AI_PRICE_STARS не
  настроен».

Что делать с `pending` возвратом: исход неизвестен (например, потерян сетевой
ответ). Сверьте Stars-транзакции бота в Telegram вручную. Повторный
`/stars_refund` по `pending` намеренно запрещён, чтобы не вернуть Stars дважды, а
автоматического повтора нет.
