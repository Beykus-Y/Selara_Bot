## 1. Цель

Три равнозначные цели одновременно, без вреда существующей экономике и истории пользователей:

1. Найти и исправить реальные баги гачи (атомарность, гонки, повторные запросы, дубли).
2. Улучшить UX/понятность существующего гача-флоу.
3. Улучшить сам pull-механик и визуальное ощущение — добавить анимированную «прокрутку»
   результата вместо мгновенной выдачи, с возможностью выбора классического режима.

Жёсткое ограничение: существующая БД гачи и история пользователей (баланс, коллекция,
питомцы/констелляции, купленные карты) не должны пострадать. Любое изменение схемы или
семантики данных — только с отдельным обоснованием, планом миграции, планом отката и явным
подтверждением пользователя, если риск реален.

Технический вывод из решения 9 (уточнено с пользователем): переход от изначального плана
«заранее сгенерировать все 195 роликов офлайн» к **лениво кэшируемым вариантам с
периодическим обновлением**:

- На (banner, card_code) хранится **несколько** (не один) закэшированных вариантов ролика
  (`telegram_file_id`), а не один статичный на всю жизнь фичи.
- При pull, приземлившемся на карту X: если закэшированных вариантов для X меньше лимита
  (предлагаю 3) — генерируем новый и добавляем в кэш; если лимит достигнут — с небольшой
  вероятностью (предлагаю ~15%) всё равно генерируем новый вариант и вытесняем самый старый,
  иначе берём случайный уже закэшированный. Это даёт разнообразие («не всегда один и тот же
  gif на конкретного перса»), но не генерирует видео на каждый pull.
- Генерация — **чистый Pillow**, без ffmpeg и без новых зависимостей: Pillow уже в
  `pyproject.toml` (`Pillow>=12.3.0,<13`), умеет писать анимированный GIF нативно
  (`Image.save(..., save_all=True, append_images=frames, duration=..., loop=0)`). ffmpeg в
  проде не установлен (в `Dockerfile` нет), поэтому решил не тянуть его как инфраструктурную
  зависимость — GIF через `send_animation` и так был согласованным форматом (решение 8).
- Кадры: фон (по одному на banner, единственный новый арт-ассет) + ряд аватарок карт того же
  банера с цветной рамкой по редкости и подписью имени, «пролетающих» и останавливающихся на
  реальной карте-результате в последнем кадре. Пролетающие персонажи — декоративная затравка
  (случайная выборка из карт того же банера при каждой генерации варианта), не влияют на
  результат и не могут быть использованы для его подмены — результат уже посчитан на бэкенде
  до начала генерации/отправки анимации.
- Кэш-таблица — **в БД основного Selara-бота**, не в БД гача-сервиса: это чисто presentation
  вопрос (как показать уже готовый результат), не экономика — не создаёт риска для данных
  гачи. Предварительная схема: `gacha_animation_variants(banner, card_code, variant_index,
  telegram_file_id, created_at)`, composite PK `(banner, card_code, variant_index)` — требует
  отдельной миграции основного бота (аддитивная новая таблица, не трогает существующие).
- Аватарки для кадров берутся тем же HTTP-путём, что уже используется в
  `_fetch_gacha_image_file` (гача-сервис отдаёт их через `/images`), так что генерация
  логично живёт в основном боте (`src/selara/`), а не в gacha-сервисе.

**Раскадровка от пользователя (`gacha_prew.png`, сохранена в контексте задачи, не в
репозитории — чисто референс механики, не ассет):**

1. `t=0` — команда принята, результат уже считается на бэкенде («Подготовка крутки...»).
2. `t=0–0.5с` — старт прокрутки: видна лента из ~7 карточек (портрет + имя + звёзды
   редкости + иконка элемента в углу), без ускорения.
3. `t=0.5–2с` — ускорение до максимума, карточки размыты (motion blur).
4. `t=2–4с` — замедление, карточки снова чёткие.
5. `t=4–5(7)с` — остановка на реальной карте-результате; у неё (и только у неё) —
   светящаяся рамка-подсветка. Остальная лента вокруг остаётся видна для контекста.
6. `t=5(7)+с` — анимационное сообщение удаляется, отправляется обычное сообщение с
   результатом (см. решение 12 — без новых типов наград, только то, что уже есть).

Итоговый тайминг укладывается в уже согласованное окно 5–7 секунд без изменений.
Фон-портал (решение 10) — единый, статичный элемент под всей лентой на протяжении всей
анимации, не меняется по кадрам.

## 3. Текущая техническая база (по итогам аудита)

- Гача — отдельный микросервис `gacha/` (FastAPI + собственный Postgres), архитектурно
  изолирован от `src/selara/` для снижения риска для основной БД. Основной бот обращается к
  нему только по HTTP через `src/selara/infrastructure/http/gacha_client.py`.
- Один HTTP-запрос = одна `AsyncSession` = одна транзакция; конкурентность внутри
  `pull`/`pull_purchase` сериализуется `pg_advisory_xact_lock` по ключу `user_id+banner`
  (`GachaRepository.lock_user_banner`). Это Postgres-only механизм — в проде реально
  используется Postgres (подтверждено `config.py`, `docker-compose.yml`, `.env.example`), так
  что это не активный баг, но footgun для любого будущего локального запуска на SQLite —
  зафиксировать явной проверкой/документацией.
- Дублирование карт обрабатывается корректно: копии 1–6 становятся
  constellation/eidolon-стадиями (не продаются), копия 7+ — «дубликат» (2x примогемов,
  продаётся по `base_currency_price * 3`). Подтверждено чтением `_resolve_reward_variant`.
- Pity/гарантий нет нигде в домене — чистый weighted-random (`rng.choices`).
- Валюта живёт per-banner в `PlayerBannerWalletModel`, отдельно от отображаемого
  `PlayerModel.total_primogems` (всегда перезаписывается при чтении).
- Двойное нажатие/повторный callback на **одном и том же сообщении** уже защищено
  (`_GACHA_MESSAGE_LOCKS`, `_GACHA_CALLBACK_IN_FLIGHT`) — покрыто тестами.
- Ambiguous-timeout проблема: нигде в стеке (gacha service → `HttpGachaClient` →
  use-case → Telegram-хендлер) нет способа отличить «запрос реально упал» от «запрос
  выполнился на сервере, но ответ потерялся». `HttpGachaClient` не делает автоповторов
  (снижает риск, но не убирает), и нет idempotency-key/recovery-проверки после таймаута.
  Конкретные проявления: «потерянная карта» в `_send_gacha_pull` (карта списана и выдана в
  БД гачи, а сообщение с результатом пользователь не получил) и возможное двойное начисление
  в `buy_currency_with_coins` (частичная компенсация уже есть, но не на все сценарии).
- Ранее была отмечена как риск гонка списания монет `economy_repo` при двух параллельных
  «купить» с двух разных гача-сообщений — **проверено и опровергнуто** (см. Этап 0):
  `add_balance` — атомарный condition-UPDATE, безопасен без доп. блокировок.
- Админ-команды (`/gachagive`, exempt-toggle, on/off toggle) — авторизация в порядке (точное
  совпадение `gacha_admin_user_id`, либо `admin_user_id`/`manage_settings` для toggle). Нет
  аудит-логирования успешных действий (только ошибки логируются). `/gachagive` без явной
  цели (reply/@username) молча выдаёт карту самому отправителю — не ошибка, а потенциально
  неожиданное поведение, стоит явно подтверждать цель в UX-этапе.
- `_check_and_maybe_restore_gacha`/`_send_gacha_skip` — это существующий **по-чатовый**
  toggle (`chat_settings.gacha_enabled`/`gacha_restore_at`) и per-user cooldown-skip
  соответственно. Не связаны с новой per-user настройкой режима анимации.
- Хранилище для новой per-user настройки «классический/анимированный режим»: рекомендуется
  колонка в `users` (`UserModel`, глобальная по `telegram_user_id`), по прецеденту уже
  существующего булева поля `subscription_exempt`. Простая аддитивная миграция, полностью
  обратно совместимая. НЕ путать с per-chat `chat_settings.gacha_enabled`.
- Существующая интеграционная инфраструктура для конкурентности реальна и проходит на живом
  Postgres (`gacha/tests/test_concurrency_postgres.py`) — покрывает бесплатный pull и sell
  после лока, но не покрывает: конкурентные **платные** pull'ы, конкурентную продажу одного и
  того же `pull_id` дважды, гонку админ-действия с реальным pull'ом.
- Документация: гача есть в `command_catalog.py` (`misc_gacha`), но полностью отсутствует в
  `docs/USER_GUIDE.md`/`docs/ADMIN_GUIDE.md`, и не покрыта существующим doc-sync тестом
  (`tests/unit/test_guide_docs_match_catalog.py`).
- Изображения карт отдаются самим гача-сервисом через `/images` (StaticFiles), в проде на
  каждый pull перезаливаются в Telegram заново вместо переиспользования `file_id` — тот же
  паттерн кэширования, который нужен для анимации, закрывает и эту неэффективность попутно.
- Переиспользуемый паттерн доставки медиа уже есть в `chat_assistant.py`:
  `bot.send_animation`/`bot.send_video` по кэшированному `file_id`, плюс `_safe_delete_message`
  для удаления временного сообщения. Планировщика задач (APScheduler) в проекте нет — принят
  паттерн `asyncio.create_task(asyncio.sleep(N) + action())`; риск — падение бота в окне
  5–7 секунд анимации оставит недосланное сообщение неудалённым (низкая вероятность/severity,
  фиксируется как принятый trade-off, не блокер).

## 4. Общие правила реализации

Тот же процесс, что был в Web UI модернизации:

- Маленькие проверяемые срезы, один срез — один коммит.
- Tests-first там, где применимо; реальная проверка (не «должно работать»).
- TODO обновляется в том же коммите, что и код.
- commit → push → CI после каждого среза; никаких ложных `[x]`.
- Не коммитить и не пушить без явной команды пользователя.
- Никаких изменений схемы БД гачи или семантики существующих данных без отдельного
  обоснования + плана миграции + плана отката + явного подтверждения, если риск реален.
- Новый анимационный режим не должен менять шансы дропа, pity (отсутствует), стоимость пула,
  награды, кулдаун, накопленный прогресс, коллекцию или любые существующие записи пользователя
  — он меняет только то, как результат доставляется в Telegram.

## 6. Матрица обязательной проверки

- Атомарность: списание валюты и выдача результата — одна транзакция, без промежуточных
  состояний, видимых пользователю как «и то, и то».
- Гонки: повторный/параллельный запрос от одного пользователя не даёт лишнего pull'а и не
  портит баланс.
- Кулдаун: корректен до/после изменений, не обходится анимационным режимом.
- Дубликаты: constellation/eidolon-логика не сломана изменениями.
- Telegram-ошибки: любой сбой отправки/редактирования сообщения не теряет и не дублирует
  результат.
- Genshin/HSR: визуально различимы в анимации; логика применяется одинаково к обеим играм.
- Совместимость: существующие данные и история читаются и отображаются без изменений после
  миграций.

## 10. Персистентный многоуровневый кэш reel-анимаций `[x]` реализовано

Пользователь запросил persistent warm-cache вместо запекания GIF в Docker-образ:
прогрев асинхронной фоновой задачей при старте, без блокировки бота; хранение вне
writable-layer контейнера (persistent volume/bind mount); детерминированная
version/hash-инвалидация вместо ручной чистки; чёткое поведение при частично готовом
или повреждённом кэше. Ниже — предложенная схема, **реализация не начата**, ждёт
подтверждения (отправлено в Telegram).

### Три уровня кэша (проверяются по порядку, от самого дешёвого)

1. **Telegram `file_id`** — уже есть в `gacha_animation_variants` (Postgres, персистентно
   переживает рестарт сам по себе). Самый дешёвый: просто ссылка, ничего не передаётся.
2. **Локальный GIF-файл на диске** — новое. На persistent volume, не в writable layer
   контейнера. Если `file_id` перестал быть валиден (Telegram иногда инвалидирует старые
   file_id) — переисполльзуем уже отрендеренные байты, просто перезаливаем в Telegram за
   новым `file_id`, без повторного Pillow-рендера.
3. **Pillow-генерация с нуля** — самый дорогой (~4-5 сек), только если нет ни валидного
   `file_id`, ни валидного локального файла.

При обычном pull: сначала пробуем file_id → если реальная отправка в Telegram падает →
локальный файл (если есть и версия совпадает) → если и его нет/не подходит — рендерим и
пишем на оба уровня.

### Версионирование/инвалидация (детерминированно, без ручных версий)

`cache_version = sha256(hash(gacha_reel.py) + hash(фоновой PNG) + ETag конкретной карты)[:16]`

- Хэш **самого файла рендерера** (`gacha_reel.py`) — не число, которое можно забыть
  увеличить: любое изменение констант/логики рендера (то, что происходило трижды за этот
  вечер) автоматически меняет хэш → весь кэш инвалидируется сам, без ручной чистки.
- Хэш фонового PNG-ассета — аналогично, при замене фона.
- ETag конкретной карты (уже есть от гача-сервиса, см. срез 4 выше) — при апдейте
  портрета ОДНОГО персонажа инвалидируется только его кэш, а не всё подряд.

`cache_version` хранится в новой колонке `gacha_animation_variants.cache_version`
(аддитивная миграция, `server_default=''` — старые записи этого сеанса автоматически
станут «неверной версии» и будут переписаны заново, никакого ручного бэкафилла).
`get_gacha_animation_variant_count`/`get_random_gacha_animation_variant_file_id`
дополнительно фильтруются по текущему `cache_version` — несовпадающие версии не
учитываются и не отдаются, просто естественно вытесняются решением 9 (evict-oldest),
так как они и есть самые старые записи.

Имя локального файла тоже несёт версию: `{CACHE_DIR}/{banner}/{card_code}/v{variant_index}_{cache_version}.gif`
— это самоописывающееся хранилище: даже если потерять всю БД, по одним именам файлов на
диске видно, какая версия актуальна, без обращения к Postgres.

### Прогрев при старте

Фоновая asyncio-задача (fire-and-forget, обёрнута в широкий `except Exception`, чтобы
никогда не уронить старт бота): для обоих активных баннеров проходит по всему каталогу
карт, для каждой карты без валидного (по `cache_version`) варианта — рендерит один,
заливает в Telegram (в ЛС `GACHA_ADMIN_USER_ID`, существующая переменная, новая не
нужна) и сразу удаляет служебное сообщение (тот же паттерн, что и в реальном pull).

«Готовность» — не просто «кэш не пуст», а **по каждой карте каждого активного баннера
есть ≥1 вариант текущей версии**. Пока не готово — animated-доставка при pull'е
показывает «Гача выполняет подготовку анимаций, попробуйте позже», а сам результат
pull'а всё равно приходит сразу отдельно (не блокируется). Довесок до 3 вариантов на
карту (решение 9) достраивается уже органически через обычный рантайм-путь, фоновой
задаче отдельно достраивать не нужно.

### Частично готовый / повреждённый кэш

- **Частично прогрето** (прогрев ещё идёт) — не проблема: уже готовые карты сразу
  используют кэш, ещё не готовые — либо ждут прогрева (глобальный гейт), либо (после
  первого полного прохода) используют существующий поштучный fallback на живой рендер.
- **Повреждённый локальный файл** (обрыв записи) — предотвращается атомарной записью
  (пишем во временный файл, затем `os.replace()` на финальное имя — стандартный паттерн,
  делает половинчатую запись невозможной в принципе, а не просто детектируемой).
- **Файл пропал с диска, а запись в БД осталась** (кто-то вручную почистил volume) —
  chтение локального файла оборачивается в try/except на `FileNotFoundError` тоже, не
  только на повреждение; трактуется как обычный промах локального кэша, откатывается на
  file_id (если жив) или на рендер.
- **Volume не примонтирован** (например, в деве без реального volume) — директория
  создаётся сама (`Path.mkdir(parents=True, exist_ok=True)`), просто без персистентности
  между рестартами в этом случае — деградация до сегодняшнего поведения, не падение.

### Инфраструктура

Новый именованный Docker volume, примонтированный в контейнер Selara (не gacha-сервиса,
рендеринг — presentation-логика Selara) — например `gacha_reel_cache:/data/gacha_reel_cache`.
Путь настраивается новой переменной `GACHA_REEL_CACHE_DIR` (дефолт для локального
запуска вне Docker — просто локальная папка в репозитории/`var/`).

## 15. Pre-deploy аудит (2026-08-18/19) — GO

Полный аудит по явному запросу пользователя, "не доверяя" TODO и прошлым выводам —
код перепроверен заново. Найдено и исправлено 6 реальных проблем:

1. **`.gitignore` не содержал `/var/`** — риск закоммитить ~2ГБ локального dev-кэша GIF
   любым широким `git add`. Исправлено (добавлена строка `/var/`).
2. **Pillow-рендер блокировал весь event loop** — `build_gacha_reel_animation` вызывался
   синхронно внутри корутины; каждый рендер (включая ~195 карт при прогреве) на 4-10 сек

   loop tick'ов во время реального рендера.
3. **Два независимых unguarded-exception "потерянный результат" бага** — ни текстовый путь

   закрывал в других местах — воспроизвёлся заново в новом коде. Исправлено на обоих

4. **Отсутствовала валидация локального GIF при чтении из кэша** — повреждённый/обрезанный

   через Pillow) в `_read_local_gif`; при невалидном файле — fallback на живой рендер.

6. **Резидуальный риск бесплатной валюты при двойном подряд неоднозначном таймауте** в

## 16. Финальный release gate (2026-08-18) — по запросу пользователя перед деплоем

1. **Concurrency прогрева**: `warm_up_gacha_animation_cache` — единственный `for`-цикл,
   каждая карта полностью `await`-ится (рендер → отправка в TG → удаление → commit) до
   перехода к следующей. Конкурентность = 1, ни `asyncio.gather`, ни параллельных
   `create_task` по картам нет — насытить thread pool или CPU параллельными рендерами
   физически невозможно при текущей реализации.
2. **Реальные замеры** (локально, тот же `gacha_reel.py`/железо, что и прод-контейнер):
   cold render (Pillow, вне кэша) — **4.56 сек/карта**; warm resolve (tier 2, локальный
   диск) — **0.01 сек**; пиковый RSS процесса во время рендера — **~850 МБ**. Карт в
   активных баннерах (genshin+hsr): **195**. Только рендер: 195×4.56с ≈ **14.8 мин**;
   с учётом реальной заливки ~9-11МБ GIF в Telegram на каждую карту (не входит в замер
   выше) полный прогрев с нуля ожидается в диапазоне **20-35 мин** — совпадает с ранее
   наблюдавшимся в живом тесте порядком величины. CPU во время прогрева — по сути один
   занятый поток на ~4.5с рендера, затем простой на время сетевой отправки; не блокирует
   остальной процесс бота (см. п.2 фикса #2 в разделе 15).
3. **Дата в имени миграции gacha-сервиса**: `20260819_0005_currency_grant_idempotency.py`
   была реальной опечаткой (mtime файла — 18.08, а не 19.08) — переименована в
   `20260818_0005_currency_grant_idempotency.py`, `revision` внутри файла обновлён
   соответственно. Проверено: нигде больше `20260819_0005` не упоминается, `alembic
   history` в gacha-сервисе строит корректную цепочку с новым именем как head.
4. **Rollback-план скорректирован** по явному указанию пользователя: **не** планируется
   автоматический `alembic downgrade` аддитивных миграций после того, как в новые
   поля/таблицы уже могли попасть прод-данные (это может тихо потерять данные, если
   откатывать после реального использования). Основной путь аварийного отката — откат
   **кода/образа** на предыдущую версию, схема БД остаётся расширенной (новые
   nullable/default-колонки и новые таблицы старым кодом просто не используются и не
   мешают его работе). Ручной `alembic downgrade` — только как осознанное отдельное
   решение, не автоматический шаг rollback-процедуры.
